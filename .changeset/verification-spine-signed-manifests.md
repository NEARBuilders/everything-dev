Manifest attribution (ADR 0046 ticket 05): the deploy train signs each slot's version manifest with the runtime's existing publish identity — the explicit publish key (`resolveSigningKey`, near-kit) or the custody wallet (OutLayer `signMessage`, `format: "raw"`) — and the chain walker verifies the signature against a key record published in the on-chain config: `publish.verification: { publicKey } | "off"` (absent ≡ off, the rollout default; unsigned manifests verify as today and old readers strip the field). The payload is the canonical key-sorted serialization the version-id derivation already uses (`signaturePayloadOf`; the `signature` field never enters the version id, like `builtAt`), so signer and verifier agree on the bytes regardless of the stored document's whitespace. The verifying key rides in the signature block, letting the walker distinguish *wrong signature* from *signed by an unregistered key* — both are the engine's tagged `SignatureInvalid`, a distinct leg in the verify report (`VerifyRemoteResult.signature`) that fails the chain hard: `bos verify` exits nonzero with an attribution column, and the smoke/adopt legs refuse the composition while the SRI legs still report. A signing identity that doesn't match the key record fails the train before anything uploads — rotation is a config publish, never a silent key swap.
