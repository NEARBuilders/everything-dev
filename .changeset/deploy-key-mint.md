feat(auth): supported deploy-key mint — `bos login --key` now mints a key that passes bundle-upload verification. The CLI login's mint switches to the auth plugin's new server-side `createDeployKey` route (the only layer that may set better-auth `permissions`): the minted key carries `bundles:write` permissions and `account`/`gateway` scope metadata matching the authored config (`--env staging` scopes to `staging.domain ?? domain`), is stored as the session credential, and is printed as `BOS_STORAGE_API_KEY=…` with a non-TTY leak warning. Deploy keys default to 365-day expiry (`--expires-in` overrides; user-keys max raised to 3650 days). The auth plugin's `verifyApiKey` now distinguishes "key lacks required permissions (bundles:write)" (`KEY_MISSING_PERMISSIONS`) from an unknown key (`KEY_NOT_FOUND`) — previously both surfaced as `KEY_NOT_FOUND`/`Invalid API key`, and the upload service maps the richer code to `FORBIDDEN`. Consumer deploy workflows gain a `storage_origin` input (default `https://upload.everything.dev`) so self-hosted `apps/upload` deployments need no template fork, and the staging workflow prefers a dedicated `BOS_STAGING_STORAGE_API_KEY` secret (for consumers whose staging domain differs) before falling back to the shared key. The upload service warns at startup when production runs on the bootstrap key without `BOS_STORAGE_AUTH_ORIGIN` (every API-key upload would fail), and its README gains the deploy checklist.
