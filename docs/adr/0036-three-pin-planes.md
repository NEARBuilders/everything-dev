# ADR 0036: The three pin planes — cross-plane verification as the security model

Date: 2026-10-21
Status: Proposed

Depends on: ADR 0001 (FastKV registry — namespace=signer, action-indexed writes), ADR 0020 (child bundle storage — CDN distribution), ADR 0021 (universal runtime image), ADR 0026 (pnpm/node toolchain — catalog pinning), ADR 0034 (platform release manifest — one pin, everything derived). Shares the hosting plane with ADR 0035 (the deploy console — thin hosting adapter, substrate-independent state, landing via branch `deploy-console/01-adr-adapter-seam`).

## Context

The dependency climate is hostile and getting more so: the Node.js November 2025 security releases carried a Brotli decompression RCE and llhttp request smuggling (CVE-2025-52922, CVE-2025-49128); Next.js shipped two critical image-optimization RCEs in a single advisory window (CVE-2025-32932/32937) after the middleware auth-bypass earlier that year; and the TanStack compromise showed shared singletons are the supply chain's favorite target — which matters to a Module Federation host that shares React across every remote. A "patch Tuesday" is now a fleet event, and for most frameworks the fleet event is: rebuild every app's image, roll every instance, hope CI holds.

ADRs 0020, 0021, 0026, and 0034 assembled a different posture — but only implicitly, spread across four documents and the deploy train's implementation. No document states the security model as a whole, so nothing forces future decisions to preserve it. The observation this ADR records: the architecture already separates every byte the system executes into **three independently-pinned planes**, and the verification of each plane's bytes lives in a *different* plane. That property — cross-plane verification — is the reason the CVE classes above map onto small, fast operations here instead of fleet-wide rebuilds. It should be named, codified, and defended before it is eroded piecemeal.

The model predates the recent incidents (the SRI machinery, digest-pinned base images, and the on-chain config all existed before the November 2025 Node releases) — this ADR is a codification, not a reaction. But the incidents are the test the model answers.

Considered and rejected: **fusing everything into the image** (the conventional Next.js posture — every deploy ships a new image; maximum rebuild surface, minimum patch velocity, and app deploys inherit the framework's rebuild latency) — rejected as the antithesis of the tier model; **verifying bundles at upload time only** (trust-the-CDN-after-publish — a later CDN compromise would be invisible to running hosts); **stale-if-error bundle caching for resilience** (availability bought by serving unverifiable pre-reset bytes after a rollback or reset — ADR 0021's fail-loud policy deliberately chose the opposite); **broadening `minimumReleaseAge` to the image plane** (the delay that protects against a freshly-poisoned npm release also delays the patch of an actively-exploited Node CVE — wrong trade on the plane where the threat is a known, patched upstream release).

## Decision

1. **Name the three planes and their pins.** Every byte a booting runtime executes is pinned in exactly one of three planes, and each plane's pin is *verified against a different plane*:

   | Plane | What it holds | Pinned by | Verified against |
   |---|---|---|---|
   | **Image** | Node runtime, node_modules, framework dists (host/api/auth logic), the in-image platform manifest | digest-pinned base (`mirror-node:24-alpine@sha256:…`, mirrored from upstream with digests preserved), deploy-time digest pin into Railway | post-publish smoke boots **that exact digest**; in-image boot assert fails the build before the smoke can |
   | **Config** | the resolved runtime config — remote URLs, shared-dep pins, tenant bindings, the platform release manifest pointer | on-chain FastKV write, signed by the account key, atomic (`__fastdata_kv`), with read-back confirmation | the NEAR account key (signature), plus local↔chain attestation (`verifyConfigAgainstChain`) |
   | **Bundles** | UI/plugin remote bytes on the CDN | sha384 SRI recorded *inside the on-chain config* (the pin plane) | the host at load time (`verifySriForUrl`), the MF fetch hook (`installIntegrityFetchHook`), the continuous watch loop (`snapshot-watch`), browser-level `integrity=` + `crossorigin` on client script tags |

   A fourth plane — **hosting**, where the image actually runs — is being introduced by the deploy-console architecture (ADR 0035): its pin is *derived* rather than hand-actuated, the reconciler converging each hosted instance to the namespace's latest published fingerprint, and the destination substrate (Fly) runs raw `image@digest` Machines — the hosting plane's pin *is* the image plane's pin, with no tag float. This matters because the incident that motivated ADR 0035 (config published, Railway service never repointed) was exactly a half-landed mutation across these planes: the imperative actuation leg ran after the config publish with a rotting credential, violating the composition rule below. Under the reconciler, "publish is the deploy" — there is no leg that can half-fail after publish.

2. **The composition rule: one plane is never enough.** A CDN compromise yields bytes that fail SRI against the config plane. A config-plane write requires the account key and is auditable on-chain; a hijacked publish is caught by `verifyConfigAgainstChain` (local SRI anchor vs chain) at boot. An image compromise must survive the digest pin — the smoke gate boots the pinned digest, not `:latest`. Therefore: **no production remote slot may load without an integrity pin** (already enforced — tenant UI/plugin overrides without `integrity` are refused in `tenant-runtime.ts`), and no deploy may promote a config whose read-back does not match. Cross-plane verification is an invariant, not an optimization; changes that add an unpinned production load path are regressions against this ADR.

3. **CVE-class → plane mapping (the operational doctrine).**
   - **Runtime CVEs** (Brotli, llhttp, TLS): image plane. Patch velocity there is the metric that matters — one rebuild patches every tier at once (root, shared-host tenants, child instances, sandboxes); children never ship images. Exposure is real and specific: the runtime's hot path *fetches and decompresses network bytes* (CDN bundles, FastKV config), and decompression happens **before** SRI verification — a Brotli-class CVE lands in `fetchResponse`, and no pin catches a decompression-stage exploit. The current mitigations are the bounded fetch (20 MB cap, fail-loud, no stale-if-error) and base-image patch speed.
   - **Serving-framework CVEs** (the Next.js class): the host surface is *this repo's* `host/` — small, first-party, and not a framework that ships per-app images. Framework packages are catalog-pinned (ADR 0026) behind Renovate `minimumReleaseAge` with minor bumps manual-only — the exact anti-pattern the TanStack incident taught.
   - **Shared-singleton supply chain**: React and the TanStack stack are shared across all remotes — the blast radius is real — but singleton bytes cannot silently change under a published config: they ship inside SRI-pinned bundles (or the digest-pinned image), so a swap is a new config publish (signed, auditable) or an SRI failure (loud).

4. **The speed asymmetry is itself a security property.** Config moves fast: app-level changes (UI, plugins) ship as build → upload → atomic publish + SRI read-back — no image, no Railway change, minutes, zero downtime via the version/soft-refresh surface. The image moves slow: rare, image-first train (the deploy order guarantees publish never precedes the image), same-SHA lockstep between image node_modules and CDN bundle pins. Fast bytes and slow bytes are separated by construction; the smoke + auto-rollback gate is what lets the fast path move fast without review theater.

5. **The security fast lane (decided): base-image digest *patch* bumps bypass `minimumReleaseAge`.** The 3-day holdback exists to catch freshly-poisoned releases; a Node security release is the opposite case — a known CVE with a known patch. The fast lane: bump the digest-pinned base + catalog in one commit (the `127afdf1` model — Node 24.22.1 + react 19.2.9 together), image-first train, smoke on the exact digest, promote. Compensating controls for the bypass: the smoke gate boots the pinned digest with health/SSR/OpenAPI/mf-check, the base mirror preserves upstream digests verbatim, and the holdback still applies to every non-security bump. Catalog *security* bumps ride the same lane only when tied to a published security release; everything else keeps the full holdback. Automation of the lane (a labeled workflow that opens and trains the bump PR) is a recorded follow-up, not built here.

6. **Prove-ability is the sovereign-software deliverable.** The three planes make "what exactly is running" answerable: the image self-describes (`bos platform manifest` — the in-image manifest carries framework version, catalog, shared deps, git SHA), the config is on-chain and inspectable, and the bundles are content-addressed by SRI in that config. Recorded future seams (not built): an image SBOM beside the manifest's catalog + `bos platform audit` (one command answering "are we exposed to CVE-X" across all three planes against OSV); a decompressed-byte cap on the bundle fetch path (closing the Brotli-class window at the pin level, not only at the image level); SLSA-style provenance attestation on the image push; the fast-lane automation from point 5.

## Consequences

- The posture under a "patch Tuesday" is: image-plane patch (fast lane) or catalog bump — one train, minutes, every tier patched — instead of N per-app image rebuilds. The asymmetry survives only if app code keeps shipping config-only; any change that fuses app bytes back into the image reopens the rebuild-latency attack window this ADR exists to close.
- Fail-loud on the bundle plane is confirmed as a security decision, not a resilience regression: a CDN outage must never fall back to unverifiable local bytes (the stale-if-error cache stays operator opt-in, and operators choosing it own the integrity gap).
- The MF fetch hook, `snapshot-watch`, `verifyConfigAgainstChain`, and the tenant-override integrity refusals are now load-bearing security controls — their failure modes (a fetch hook silently deregistered, a watch loop swallowing mismatches) should get the same test rigor as auth.
- The known window stays open until the fetch-path seam lands: network-fetched bytes are decompressed before SRI applies. Bounded fetch mitigates; it does not close.
- Future work should cite this ADR when touching any of: the deploy train's leg order, the SRI machinery, base-image pins, the Renovate config, or the smoke gate — each is a plane boundary, not just plumbing.
