## Question

How does the host support both `app.ts` and `bos.config.json` during transition?

The user's preference: host prefers `app.ts` if present, falls back to `bos.config.json`.

But this raises several concrete questions:

1. **Detection mechanism** — how does the host know which format to read? Does it check for `app.ts` in the resolved tenant's published config? Does the FastKV entry have a `format` field (`"app-ts"` vs `"bos-config"`)?
2. **Internal representation** — after reading either format, does the host normalize to a common internal type? Today `RuntimeConfig` is derived from `bos.config.json`. If `app.ts` has a different shape (e.g., `web: { dashboard: WebPlugin(...) }` vs `plugins.dashboard.ui.url`), the host's consumption code needs to handle both.
3. **Tenant resolution** — for Tier 1 tenants (subdomain on shared host), the tenant's config might be `app.ts` while the base runtime's config is `bos.config.json` (or vice versa). How does the host merge/override across format boundaries?
4. **Child repo upgrade path** — existing child repos generated by `bos init` have `bos.config.json` and depend on `sync.ts`/`snapshot.ts`. When those are removed in v2, how do existing child repos upgrade? Options: a one-time migration script (`bos migrate`), manual migration guide, or automatic conversion on `bos publish`.
5. **`app.ts` authoring experience** — does `app.ts` live in the child repo (tenant writes their own), or is it generated by `bos init`? If generated, what's the template?
6. **Dual-write** — during transition, does `bos publish` write both formats to FastKV? Or does the host normalizer handle the conversion?

Effect.ts perspective: can the host define a `Config` Tag with two Layer implementations — `BosConfigLayer` (reads `bos.config.json`) and `AppTsLayer` (reads evaluated `app.ts`) — and select based on the published format?
