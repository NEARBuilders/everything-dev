# 02 · Anatomy of a runtime

A runtime is assembled from a small number of parts with strict jobs. Each part owns
one concern, and no concern has two owners. Knowing which part owns what is the
fastest way to find where a change belongs.

## The parts

| Part | Owns | Built on |
|---|---|---|
| `host/` | Serving: HTTP, mounting every plugin's API, the Module Federation host, SSR, per-request tenant resolution, the agent surfaces | Hono, oRPC, Effect |
| `ui/` | The core UI: routes, the design system, the `@/app` surface every UI imports from | React 19, TanStack Router and Query |
| `api/` | The slim app-level API: a few routes and the database layer | oRPC, Effect |
| `plugins/*` | Features: auth, registry, proposals, votes, ai, docs, agent-connect | `every-plugin` |
| `packages/everything-dev` | The `bos` CLI and the framework: dev session, build and deploy train, config resolution, scaffolding, the database and UI runtimes | Effect |
| `packages/every-plugin` | The module seam: `createPlugin`, the build composition, the plugin runtime | rspack, Module Federation |
| `packages/better-near-auth` | Sign in with NEAR for Better Auth | Better Auth |
| `apps/` | The destination shape: standalone, verifiable apps and a runtime that composes them | — |
| `infra/`, `tests/regression` | Infrastructure as Effects; the full-stack regression suites | alchemy, Go, Playwright |

The three packages publish to npm. Apps built on the platform install them and never
carry a copy of their code — which is why a framework fix reaches every app with one
version bump.

## One contract, many surfaces

Every `bos` command is a procedure in one oRPC contract
([`packages/everything-dev/src/contract.ts`](../../packages/everything-dev/src/contract.ts)).
The CLI calls it through a typed client; the REST API, the OpenAPI spec, and the MCP
server are generated from the same contract. A command, an HTTP route, and an MCP
tool are three views of one procedure.

Inside the package, the layering runs one way — `cli → contract ← handlers →
services` — with services holding all domain logic as Effect tags and layers, and
the CLI as presentation only. ([ADR 0031](../adr/0031-package-shape.md))

## How a request travels

Every request reaches the host first, and the host decides what serves it:

| The request | Served by |
|---|---|
| A page | SSR — the host composes the route tree from every UI remote's manifest |
| `/api/rpc/<plugin>/*` | The plugin, loaded in process |
| `/api/*` | The OpenAPI mount, generated from the contracts |
| Static assets | The UI bundles — from the CDN in production, from dev servers locally |

Plugins load in two phases. The host first loads every non-API plugin and assembles a
`pluginsClient` map — each entry a typed client plus the plugin's raw router — then
loads the API with that map injected. A plugin calls another plugin's routes through
that map, in process, with no HTTP hop.

## How much is your own

An app's files fall into three classes, and the distinction matters whenever you edit
something:

| Class | Examples | Who changes it |
|---|---|---|
| App-owned | Routes, components, `contract.ts`, `router.tsx`, `app.ts` | You, freely |
| Framework-owned | Build configs, workflow templates, `docs/agents/` | `bos sync` reconciles it from the template |
| Generated | `*.gen.*` — route trees, types, entries | `bos dev`, `bos build`, `bos typecheck` |

Editing a framework-owned file is allowed; making the change permanent goes through
the upstream-change protocol in [12 · Contributing](12-contributing.md). Never edit a
generated file.

## The map of who owns what

Ownership questions — *who owns `/settings`? which auth plugin version is composed?
is this path served locally or by a remote?* — are answered from generated state, not
by searching dependencies:

- `.bos/generated/runtime-map.json` inventories every UI source, every route with its
  owner, and every backend with its version and contract hash.
- `ui/src/lib/runtime-map.gen.ts` is its typed form.

Both are regenerated by `bos types gen`. See [the runtime map](../agents/runtime-map.md).

## Check it

- `bos plugin list` — the plugins this runtime composes.
- `bos ps` — the running processes, their roles, and ports.
- `bos config` — the resolved config, including which remotes are local overrides.
